# Kubernetes 最新版部署与维护计划（企业可落地版）

## 1. 目标与范围

- **目标版本**：以 Kubernetes 最新稳定版（Stable）为目标，采用“小版本可控升级”策略。
- **部署范围**：生产集群（HA）、预发布集群（Staging）、测试集群（Dev/Test）。
- **核心目标**：
  - 高可用（控制面多副本、关键组件冗余）
  - 可观测（日志、指标、告警闭环）
  - 可升级（标准化升级窗口与回滚预案）
  - 可审计（RBAC、镜像与配置变更可追踪）

---

## 2. 总体架构设计

### 2.1 集群形态

- **控制平面**：3 台（奇数）Master 节点，`kube-apiserver`、`kube-controller-manager`、`kube-scheduler` 高可用。
- **etcd**：
  - 方案 A：与控制平面同机（中小规模）
  - 方案 B：独立 3/5 节点 etcd（推荐生产）
- **工作节点**：按业务池化（通用池/GPU 池/高内存池），打标签和污点隔离。
- **容器运行时**：`containerd`。
- **CNI 网络插件**：Calico 或 Cilium（二选一，建议先 Calico，追求 eBPF 能力可选 Cilium）。
- **Ingress**：Nginx Ingress 或 Gateway API（按现网能力选择）。

### 2.2 环境分层

- **Dev**：快速验证，允许更高变更频率。
- **Staging**：与生产同构，进行升级演练与压测。
- **Prod**：严格变更窗口、分批升级、可回滚。

---

## 3. 部署实施计划（分阶段）

## 阶段 0：项目准备（T-2~3 周）

1. **资产盘点**
   - 服务器规格、网络、存储、GPU 型号与驱动。
   - 业务清单、命名空间规划、SLA/SLO 要求。
2. **版本与兼容性确认**
   - Kubernetes Stable 版本。
   - CNI、CSI、Ingress、监控栈兼容矩阵。
3. **镜像与制品策略**
   - 私有镜像仓库、镜像签名与漏洞扫描。
4. **安全基线**
   - 操作系统加固（CIS 基线参考）
   - kube-bench、kube-hunter 评估计划。

**交付物**：版本选型文档、兼容性清单、风险清单、上线里程碑。

## 阶段 1：基础设施准备（T-1~2 周）

1. **主机初始化**
   - 时钟同步（NTP/Chrony）
   - 关闭 swap、配置内核参数（`br_netfilter`、`ip_forward`）
   - 安装 `containerd`、`kubeadm`、`kubelet`、`kubectl`
2. **网络准备**
   - Pod 网段、Service 网段规划并避免与现网冲突。
   - 负载均衡/VIP（用于 API Server 高可用入口）。
3. **存储准备**
   - CSI 驱动（云厂商盘、本地盘、Ceph/NFS 等）
   - StorageClass 分层（高性能/通用/低成本）

**交付物**：可重复执行的初始化脚本（Ansible/Terraform + Shell）。

## 阶段 2：集群安装（T-1 周）

1. **使用 kubeadm 部署 HA 集群**
   - `kubeadm init` 初始化首个控制平面。
   - 其余控制平面 `kubeadm join --control-plane`。
   - 工作节点 `kubeadm join`。
2. **安装 CNI、CoreDNS、Metrics Server**。
3. **部署基础组件**
   - Ingress Controller
   - cert-manager
   - ExternalDNS（可选）
   - 备份工具（Velero）

**验收标准**：
- 所有节点 `Ready`
- CoreDNS 正常解析
- 基础服务可发布并可外部访问

## 阶段 3：平台能力建设（T+1~2 周）

1. **可观测性**
   - 指标：Prometheus + Grafana
   - 日志：Loki/ELK
   - 告警：Alertmanager（值班通知通道）
2. **安全与合规**
   - RBAC 最小权限
   - Pod Security Admission
   - 镜像扫描（Trivy）
   - Secrets 管理（KMS/Vault）
3. **交付规范**
   - Helm/Kustomize 统一发布模板
   - GitOps（Argo CD/Flux）

**验收标准**：
- 核心监控看板与告警可用
- 关键命名空间权限隔离完成
- 发布流程可审计

## 阶段 4：生产切换与验收（T+2~3 周）

1. 业务灰度迁移（低风险业务先行）
2. 容量与性能压测（CPU/内存/网络/存储）
3. 故障演练（节点宕机、组件重启、网络隔离）
4. 正式切换与运行评审

---

## 4. 运维维护计划（长期）

### 4.1 日常运维（每日/每周）

- **每日**
  - 检查集群健康（节点状态、组件状态）
  - 查看告警、异常事件、失败发布
- **每周**
  - 容量趋势复盘（CPU/内存/磁盘/Pod 数）
  - 失败任务与 OOM 分析
  - etcd 健康与快照验证

### 4.2 版本升级策略（每月/每季度）

- **原则**：仅跨一个小版本升级（如 `v1.x -> v1.(x+1)`）。
- **流程**：
  1. 在 Staging 完整演练。
  2. 先升级控制平面，再升级节点池。
  3. 分批滚动升级，每批设置观察窗口。
  4. 升级后执行回归测试与性能对比。
- **回滚预案**：
  - 保留旧节点池，支持业务快速回迁。
  - etcd 快照可恢复。

### 4.3 备份与恢复（DR）

- **备份对象**
  - etcd（核心）
  - 关键命名空间 YAML 资源
  - 持久卷数据（按业务等级）
- **频率建议**
  - etcd：每日全量 + 关键变更后补充快照
  - 应用数据：按 RPO 设定（例如 1h/4h/24h）
- **演练**
  - 每季度至少一次恢复演练并出报告。

### 4.4 安全维护

- 节点 OS 与容器运行时补丁定期更新。
- 镜像漏洞扫描门禁（高危漏洞阻断上线）。
- API 审计日志保留与定期审查。
- 高危权限（`cluster-admin`）最小化并可追踪。

## 5. 组织与职责（RACI 简版）

- **平台团队（负责）**：集群部署、升级、监控、容量规划。
- **业务团队（协作）**：应用改造、SLO 定义、灰度与回归验证。
- **安全团队（审计）**：基线检查、漏洞处置、权限审计。
- **运维值班（执行）**：告警响应、故障升级、事件复盘。

---

## 6. 风险清单与应对

1. **版本不兼容风险**：先做兼容矩阵和预发布演练。
2. **升级中断风险**：分批升级 + 可回滚节点池。
3. **资源不足风险**：建立容量阈值告警与自动扩容策略。
4. **配置漂移风险**：GitOps + IaC 管理，禁止手工改生产。
5. **单点故障风险**：控制面、etcd、Ingress、监控全链路高可用。

---

## 7. 建议里程碑（示例）

- **第 1 周**：完成架构设计与版本选型。
- **第 2 周**：完成基础设施准备与自动化脚本。
- **第 3 周**：完成 Staging 集群部署及平台组件接入。
- **第 4 周**：完成生产部署、灰度迁移与验收。
- **第 5 周起**：进入持续运维（升级、备份演练、优化）。

---

## 8. 建议的首批执行清单（可直接开工）

1. 确认 Kubernetes 目标版本与兼容矩阵。
2. 输出节点规划表（Master/Worker/GPU 池）。
3. 编写并评审主机初始化脚本。
4. 在 Staging 完成 kubeadm HA 部署与 CNI 验证。
5. 上线 Prometheus/Grafana + Alertmanager。
6. 打通备份恢复流程（etcd + 应用数据）。
7. 组织一次“升级演练 + 故障演练”。
8. 冻结生产变更窗口并执行灰度上线。
